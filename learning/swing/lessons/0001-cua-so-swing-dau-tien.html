Cửa sổ Swing đầu tiên: JFrame và Event Dispatch Thread

Nền tảng của mọi ứng dụng Swing — bất kể ứng dụng đó có bao nhiêu màn hình.

Nguồn chính Đọc trước (5-10 phút): Oracle — Getting Started with Swing và Oracle — The Event Dispatch Thread. Bài học này chỉ tóm tắt đủ để bạn bắt tay vào code; hai trang trên là nơi giải thích đầy đủ "vì sao".

1. Vì sao Swing "khó tính" về luồng (thread)?

Hầu hết các phương thức của component Swing (JFrame, JButton, JTable, ...) không an toàn khi gọi từ nhiều luồng cùng lúc. Nếu hai luồng cùng sửa một component, kết quả có thể sai lệch hoặc treo ứng dụng một cách rất khó debug. Vì vậy Swing quy định: toàn bộ việc tạo/sửa component phải chạy trên một luồng riêng gọi là Event Dispatch Thread (EDT).

Tin tốt: sau bước khởi động, bạn hiếm khi phải chủ động nghĩ về EDT nữa. Mọi nút bấm, mọi lựa chọn trong bảng đều tự động chạy callback trên EDT rồi. Nơi duy nhất bạn chủ động nhảy vào EDT là lúc chương trình khởi động, trong main: 

public class MyApp {
    public static void main(String[] args) {
        SwingUtilities.invokeLater(() -> {
            // Toàn bộ code tạo UI đầu tiên nằm ở đây, không phải ngoài invokeLater
            JFrame frame = new MyFirstWindow();
            frame.setVisible(true);
        });
    }
}

invokeLater xếp đoạn code của bạn vào hàng đợi của EDT thay vì chạy ngay trên luồng main — đó là cách "bàn giao" việc tạo UI cho đúng luồng. Đây là khuôn mẫu chuẩn cho main của bất kỳ chương trình Swing nào, không riêng ứng dụng nào cả.

2. Khung JFrame tối thiểu

JFrame frame = new JFrame("Tiêu đề cửa sổ");
frame.setDefaultCloseOperation(JFrame.EXIT_ON_CLOSE);
frame.setSize(1000, 700);
frame.setLocationRelativeTo(null); // căn giữa màn hình
frame.add(new JLabel("Xin chào Swing!"));
frame.setVisible(true); // luôn là dòng cuối
Lỗi hay gặp Gọi setVisible(true) trước khi thêm hết component, hoặc quên nó luôn (cửa sổ không bao giờ hiện). Thứ tự đúng: cấu hình xong xuôi → add component → setVisible(true) cuối cùng.

3. Áp dụng vào một ứng dụng thật

Bất kỳ ứng dụng Swing nhiều màn hình nào — kể cả app bạn đang xây — cũng bắt đầu từ đúng hai khối kiến thức ở trên: một main bọc trong invokeLater để mở cửa sổ đầu tiên (thường là màn hình đăng nhập hoặc màn hình chính), và bên trong cửa sổ đó là một khung JFrame cấu hình đúng thứ tự như mục 2. Từ đây, việc "có nhiều màn hình" chỉ là thêm layout/component vào bên trong cùng một khung này — bài học sau sẽ nói kỹ hơn về cách bố cục nội dung bên trong (BorderLayout, JPanel) và cách chuyển qua lại giữa nhiều màn hình (CardLayout).

Kiểm tra nhanh

1. Tại sao mọi thao tác với component Swing phải chạy trên Event Dispatch Thread (EDT)?

Đúng — component Swing không thread-safe, gọi từ nhiều luồng dễ gây lỗi khó tái hiện.
Chưa đúng. Gợi ý: vấn đề nằm ở chính component Swing, không phải mạng hay Java nói chung.

2. Thêm một JTable thẳng vào JPanel mà không bọc trong JScrollPane thì điều gì xảy ra?

Đúng — không có lỗi, không crash, bảng vẫn chạy được, nhưng dòng tiêu đề cột biến mất.
Chưa đúng — không có crash hay lỗi dữ liệu nào cả, chỉ là thiếu mất một phần hiển thị.

3. Sau khi thay đổi dữ liệu bên trong một AbstractTableModel tự viết, quên gọi phương thức nào sẽ khiến JTable không bao giờ cập nhật lại giao diện?

Đúng — đây là phương thức thật của AbstractTableModel, ba lựa chọn còn lại không tồn tại.
Chưa đúng — ba phương thức kia không tồn tại trong Swing, chỉ là tên gây nhiễu.

Bài tập thực hành

Viết code thật, biên dịch và chạy thật — không chỉ đọc rồi lướt qua.

  1. Tạo một file MyFirstWindow.java ở bất kỳ đâu bạn muốn thử nghiệm, biên dịch bằng javac và chạy bằng java trực tiếp (không cần Maven/Spring cho bài tập này).
  2. Viết một main method: bọc toàn bộ code tạo UI trong SwingUtilities.invokeLater(() -> { ... }) như mục 1.
  3. Bên trong, tạo một JFrame với tiêu đề "Bài tập 1", kích thước 400x300, căn giữa màn hình, và thêm một JLabel hiển thị tên của bạn.
  4. Cố ý phạm lỗi mục 2 trước: gọi setVisible(true) trước khi thêm JLabel, chạy thử, quan sát điều gì xảy ra (hoặc không xảy ra). Sau đó sửa lại đúng thứ tự và chạy lại để thấy sự khác biệt.
  5. Tự kiểm tra (không cần ai chấm):
    • [ ] Cửa sổ hiện đúng giữa màn hình, đúng kích thước 400x300.
    • [ ] Đóng cửa sổ (nút X) thì chương trình thoát hẳn (do EXIT_ON_CLOSE).
    • [ ] Bạn giải thích được bằng lời của mình: tại sao đoạn code UI nằm trong invokeLater chứ không gọi thẳng trong main.
  6. Áp dụng vào project của bạn: mở file nơi ứng dụng của bạn khởi động cửa sổ đầu tiên (thường là nơi chứa public static void main) và kiểm tra: nó có đang bọc việc tạo UI trong invokeLater đúng như mục 1 không? Nếu ứng dụng chưa tồn tại, giữ nguyên đoạn code bạn vừa viết — đó chính là khung sườn bạn sẽ dùng.
